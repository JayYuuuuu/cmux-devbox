# DevBox 独立调色浮窗：需求上下文与实施计划

> 状态：供 Claude Code 只读审核的方案，尚未批准实施。日期：2026-11-05。
> 本轮只整理上下文与计划，不新增调色功能、不合并候选、不发布应用、不改服务器或用户配置。
> 用户要求的是实际使用界面上的所见即所得，不是另做一张看起来相似的预览图。

## 1. 为什么提出这个需求

用户最近使用的 DevBox 外观已经经过较大调整，整体风格得到认可。原来的三个自配深色主题观感偏灰，Claude Code 底部 HUD 的用量颜色不够明显；第四套 Forest 是用户当时最满意、要求保留的参考。

本轮先做了一次有限替换：前三个深色主题改成 Catppuccin Mocha、Tokyo Night Night、Dracula，Forest 和四套浅色保持不变。用户随后指出：每次调整颜色都需要改代码、构建试用包、人工确认、再发版，若仍不满意还要重复，维护与试用成本不合理。

因此目标从“替换三套默认配色”，扩大为“让用户自己精调八套主题，并可保存、复用和在多台电脑间共享”。前三套替换只是现有候选基础，不是新需求的最终交付。

## 2. 用户明确提出的要求

以下是需求，不应在实现中降级为单纯修改主题文件或增加普通设置项：

- 现有八个自定义主题都能独立调整细节，保留每套风格，不是一个全局颜色覆盖全部主题。
- 希望自己选择终端文字、代码，以及不同模块的颜色。
- 入口就在正常使用界面；直接调出独立浮窗，不必进入设置页与原来的设置混在一起。
- 选颜色以后，在正在使用的真实窗口立刻看到变化；不接受只有示意预览有效、实际界面要重启才能看到的体验。
- 配色应独立于应用代码，可以保存和引用；允许放到自有服务器，方便自己使用和多设备复用。
- 调整已有颜色不再依赖开发者逐次修改、构建、问是否满意、发版。
- 原来的三套自配深色主题必须完整备份，方便以后找回。

用户原话中的关键约束：

> “我们自定义的这8个主题要调整颜色，能不能就在外面直接调出一个浮窗让我选择，省得进入设置页面去和原来的混在一起？”
>
> “我要的只是所见即所得，点了以后立马能看到变化，在这个实际生产界面上。”

用户会在不同 Mac 上工作。交付与验收必须确认当前设备，不能用默认日常机代替当前设备。当前设备和私有交付位置见本地未跟踪的 `CLAUDE.local.md`，不把设备名、主机地址、凭据写进公开仓库。

## 5. 必须先厘清颜色归谁控制

这是审核最重要的边界，不能用一个取色器掩盖多个实际控制源。

### 5.1 DevBox 自己的界面

背景、卡片、边框、侧栏、选中态、团队状态点、用量条、Claude/Codex 标签等，应由一份有效主题数据提供。各模块消费同一来源；不要分别写 JSON、Swift 常量、JS 常量，最终互相覆盖。

### 5.2 终端默认颜色与调色板

默认正文、背景、光标、文本选择、ANSI 基础/亮色以及淡化效果由终端处理。已有 Ghostty 配置可以承载这些值，不新造终端渲染器。

注意：“辅助文字”可能是单独的灰色，也可能是程序对当前正文施加淡化。只修改 ANSI 8 不一定改变所有灰字；浮窗里的名称和效果必须与真实输出对应。

### 5.3 Claude Code、Codex、HUD 与其他终端程序

终端拿到的是字符和颜色指令，通常不知道哪个字符是关键字、字符串、注释或错误。程序若直接输出 RGB，不能承诺改终端的基础蓝色就会跟着变。

- Claude Code 官方文档已有自定义主题、颜色语义项和热更新说明，可作为适配入口；是否完整适用于当前安装版本、深浅自动切换、tmux 与正在运行的会话，仍需最小实际验证。
- Codex 的代码高亮、界面颜色和刷新边界要核对当前版本及官方支持能力。此计划不把“终端支持换主题”当成“任意语法颜色都已能独立调整”的证明。
- HUD 有自己的颜色配置，应复用其正式配置能力，不改插件安装包；确认插件升级后仍有效。
- 远端 tmux 状态栏已存在跟随终端的规则，不随手增加第二套色表。现有深浅、输入框/差异背景适配也必须检查交互影响，不盲目替换。

每个控制项都要能回答：它影响哪个真实组件、在哪台机器生效、是否影响其他连接、何时可见、能否还原。无法兑现的项目暂不显示为“可调”，也不能因此把用户的代码/模块需求悄悄删掉；需记录为待适配或待用户接受的限制。

## 6. 推荐交互：独立、非模态、直接看实际界面

以下是建议方案，供审核，不是用户已确认的每一个交互细节。

- 八个色点附近增加一个清楚的调色入口；右键某个色点可直接编辑那套主题，二者调用同一动作。不强制增加新快捷键。
- 使用可移动的原生浮窗，限本应用工作时显示，不做全系统永远置顶。打开时尽量避开正文，记住位置；切到其他工作区后不绑定错误窗口。
- 浮窗顶部明确“当前编辑的主题”和是否有未保存修改。初始只围绕现有八套主题，不先扩成主题商城或大型设置中心。
- 按用途分组显示颜色：终端、工作区/侧栏、团队面板、程序适配。使用中文名称、色点和色值；解释放提示，别把技术键名直接暴露给用户。
- 用户选中控制项、连续拖动颜色，当前实际窗口实时反馈。不能只改浮窗里的示意预览，也不能要求离开当前界面看效果。
- 保留撤销/重做、取消还原、恢复出厂值、保存；另存为或导入导出复用同一配置模型，不改动原始出厂资源。
- 未保存时切主题或关闭浮窗的行为必须明确。建议仅在这些会丢修改的边界提供“保存 / 放弃 / 继续编辑”，不在每次改色时询问。也可审核更简洁且不会丢草稿的方案。
- 改色不能重建会话、断 SSH、清空终端、改变中文字体、抢正文输入焦点或影响图片粘贴。用户主动点击取色器时的正常焦点变化与后台刷新抢焦点要区分。

颜色范围建议：

| 分组 | 首批需要核实和覆盖的项目 |
| --- | --- |
| 终端 | 正文、背景、辅助/淡化文字、光标、选择文字/底色、16 个基础/亮色 |
| 工作区外观 | 外层底色、卡片边框、活动/非活动分屏边框、页签文字及选中提示 |
| 团队面板 | 卡片、正文/辅助文字、选中描边与填色、工作中/等待/完成/退出、用量正常/警告/临界、标签 |
| 程序适配 | Claude 消息/提示/差异背景、HUD 用量和标签、Codex 能正式支持的语法与界面颜色 |

这是调查和验收清单，不表示每一项都已有配置接口。调查后应标注“复用现有 / 需新增 / 当前不支持”，再冻结第一版范围。

## 7. 推荐数据与保存方式

### 7.1 两个选项

**A：只存本机。** 接入少、离线完整；其他电脑靠导入导出。不能满足自动跨设备复用。

**B：本机即时应用，自有服务器保存与共享。推荐。** 本机编辑与预览不依赖网络；服务器保存命名主题和历史版本，其他电脑主动获取或按选定策略更新。相较 A 多了同步、版本与冲突处理，但更符合用户多设备使用的场景。

不建议把每次拖动颜色变成服务器请求，也不建议只读远端、没有有效本地副本。最终选项、服务承载位置、现有认证复用方式尚需确认，不能把“允许放服务器”理解为已授权新建账号系统或部署到任意机器。

### 7.2 单一主题来源与应用映射

- 每套主题有稳定 ID，显示名可变；旧主题别名兼容，不能按显示名当永久主键。
- 出厂主题只读，用户版本独立持久化，应用升级不覆盖。
- 建议把用户保存时的完整有效配色作为权威快照，并记录来源主题和格式版本。避免仅存差量、升级后基底变化导致用户保存的颜色悄悄改变。若选择“固定版本基底 + 覆盖”，必须证明旧基底升级后仍可取得；审核时二选一，不同时保留两套可写真相。
- 应用内颜色、生成的 Ghostty 主题、必要的程序适配配置都是同一主题的消费结果。明确哪些是用户手工文件、哪些是工具拥有的派生结果及重建规则。
- 现有显式颜色设置不能被浮窗静默盖掉。进入编辑时先解析真实生效值及覆盖关系；必要时显示“被现有设置覆盖”，由用户决定是否纳入主题管理，只修改归本功能所有的部分。
- 持久化区分：已保存主题、当前选择、临时预览、服务器版本。关闭/崩溃后不能把未确认的临时文件当正式主题，也不能丢掉以前的有效配置。

### 7.3 本机预览与服务器共享必须分开

“保存到本机”与“同步到共享库”语义分开。编辑时不推动其他电脑立即变化；获取共享主题也不直接覆盖当前未保存草稿。网络失败保留最后有效副本并允许重试，不回退到一套看不见文字的空配置。

共享写入带版本条件，冲突保留双方内容，可另存或比较；禁止最后写入者直接覆盖所有设备的修改。服务端提供版本历史与恢复；超出当前客户端认识范围的字段要有明确兼容策略。

服务器只接收经过校验的配色数据，不把下载主题当成能执行命令的完整 Ghostty 配置。自有服务器也不等于可以跳过颜色类型、大小、格式和版本检查。

### 7.4 远端程序不是本机配色的简单延伸

一台 Mac 的终端颜色可以本机试；远端同一个 Claude/Codex/tmux 会话可能有多个客户端。改远端程序自身主题可能同时影响其他连接。

界面应区分“本机外观”和“远端共享会话”。普通本机拖色不能悄悄改远端各账号配置；需要改程序配置时，明确目标、作用范围、备份和恢复，并复用已有连接与配置管理。不得靠追加无边界的远端命令或放宽 socket relay allowlist 实现。

## 8. 实时应用的实现约束

- 预览、保存、取消、恢复默认、CLI 与现有主题按钮，共用一条应用路径；不让每个入口维护独立副本。
- 开始编辑时记录当前选择和本功能负责字段的基线；预览有会话标识/版本。过时的异步结果不能覆盖最新颜色，取消后不能被迟到回调重新改回。
- 连续拖动合并中间值，最终值必达；优先细粒度更新。先量现有重载代价，不能每次颜色变化都同步重写全配置、发全局重载、重建终端。
- 预览期间若有外部配置修改，检测并处理冲突。取消只撤销自己的预览，不能整份旧配置覆盖其他修改。
- 写文件采用原子替换或现有安全写入能力；保存失败仍保留可恢复的草稿和最后有效主题。覆盖导入前保留原版。
- 预览不需要常驻轮询服务器；新增观察者、任务和订阅随浮窗/应用生命周期正确释放。
- 仅在 `CmuxDevBoxEdition` 的既有边界内启用；不改变其他 bundle id 的行为，不重新启用上游账号、Cloud、手机入口。
- 按现有架构分层组织：纯主题值和解析、持久化与同步、编辑状态与协调、浮窗 UI、应用组合接线。新包是否必要由真实依赖边界决定，不先按每个小能力各建一个包。

## 9. 分阶段实施与停止条件

### 阶段 0：审核与最小可行验证

1. Claude Code 先只读审核本文、真实入口、现有配置/颜色消费链与项目约束，给出问题和修订建议，不自行开始实现。
2. 确认 A/B 保存方案、第一版覆盖范围、浮窗草稿语义及多窗口/远端共享作用范围。
3. 审核通过并获得实施授权后，做最小验证：原生取色连续变化能否通过现有路径更新真实终端；团队面板如何引用主题；当前 Claude/Codex/HUD 的正式主题接口和实际刷新行为。
4. 输出能力映射和实测记录。若某控制项不能立即反馈，明确缺口及替代办法，不先承诺全覆盖。

### 阶段 1：完整本机调色闭环

- 把八套默认主题注册、用户版本、当前选择与已编辑状态接入同一来源；旧名称与原三套备份保留。
- 实现独立浮窗、取色、实际界面预览、撤销/取消、恢复出厂、保存与必要的导入导出。
- 接通本次冻结范围内的 DevBox 模块、终端和已验证的程序适配，清理本次触及范围内的硬编码双份来源。
- 接入已有配置/重载体系，保留无网络使用、升级保护、冲突与崩溃恢复。
- 阶段验收必须是用户能自行把某套主题调好、保存、重开仍保持，不需要开发者再次构建。只做一个展示用取色面板不算完成。

### 阶段 2：自有服务器共享

若采用推荐 B，这也是完整交付范围，不能把阶段 1 当成全部完成后遗忘。

- 先盘点既有服务、存储、认证与备份，选定复用方案；部署目标单独核实，不在本计划中虚构地址或凭据。
- 接入主题保存、获取、版本条件写入、历史恢复；本机与服务器同步状态明确。
- 验证两台设备并发编辑、离线编辑后恢复网络、旧客户端读取新格式、同步失败及冲突。
- 普通用户调色不触发应用发布。新增可调组件或修改同步协议等程序能力，仍可能需要软件更新。

### 阶段 3：真实设备交付与一次正式发布

- 使用项目规定的构建/签名/发布脚本，提交推送与候选源码对应。
- 将候选交到用户当前实际使用的设备，在真实生产界面由用户自己打开浮窗调色；不得用另一台机器或离屏示意图代替。
- 用户确认该版交互与外观后才合并、发布；运行行为若在验收中改了，必须重新交付候选，旧确认不自动覆盖新版本。
- 同步用户说明、配置格式/恢复文档与发布说明。此后日常配色修改走数据保存/共享，不再走发布流程。

## 10. 验收清单与证据要求

### 功能与数据

- 八套主题逐套改一个代表性颜色，确认只改变目标主题；切换、保存、重开、重启应用仍正确，出厂值与旧自配备份可找回。
- 同一颜色在浮窗、侧栏、终端、设置或 CLI 等相关入口最终一致；不出现按钮已选中、实际主题没变的乐观假象。
- 连续拖动后停止、迅速改另一个颜色、切主题、撤销、取消均以最后有效操作为准；保存失败、坏文件、崩溃和外部修改不造成数据丢失。
- 在实际 Claude/Codex/HUD 中检查正文、辅助字、输入/消息底色、代码块、差异背景与用量条；按能力映射分别记录，不用其中一个程序的成功代表全部。
- 多窗口、不同深浅主题、共享远端会话要明确范围，不允许本机试色偷偷改变其他设备的个人主题。

### 性能与可读性

- 实测拖动事件到真实组件最终颜色的延迟、刷新/重载次数、拖动期间及停止后的 CPU/内存、正文键入响应，给出改前/改后结果；不凭“用了合并更新”宣称流畅。
- 建议把“停止拖动后 200ms 内最终颜色到达实际界面”作为待确认的本机反馈目标，**这是拟定验收目标，不是已测结果或已承诺能力**；实施验证后冻结标准。网络同步不计入本机预览关键路径。
- 默认配色和新 UI 控件满足项目文字/选中态规范；测量透明度合成后的颜色，先用黑白等正对照证明判据有效。
- 用户自行选出低对比颜色时给轻提示与一键恢复，不在每次拖动弹阻断确认，也不静默把用户选色替换成别的颜色。

### 项目门禁

遵循 `AGENTS.md` 与相关技能的最小充分验证：项目规范化、测试登记、受影响包与相关原生用例、实际配置读写及热更新。新增行为用行为测试覆盖，不用 grep 源码或静态配置形状冒充测试。

新用户界面文字按项目全部支持语言做本地化审计；精确主题资源标识的例外不能代替新增界面文案的翻译。触及图片粘贴或 SSH 识别路径时，额外执行项目规定的真实远端 Codex Cmd+V 验收。

## 11. 请 Claude Code 重点审核的问题

1. 方案是否准确保留了“八套、独立浮窗、真实界面立即生效、模块和代码颜色、自主保存复用、不反复发版”的全部要求？有没有把需求缩减成终端基础色修改？
2. 哪些颜色现在可以直接复用底座，哪些必须新增共享配置，哪些属于远端程序控制？引用实际代码和当前版本证据，不按模块名猜。
3. 数据的唯一权威来源、出厂值、用户版本、现有显式配置的优先级是否清楚？升级、取消、并发外部编辑会不会丢修改？
4. 连续取色能否避免重复全局重载、重建终端和输入卡顿？应该复用/补充哪一个现有应用路径？
5. 原生浮窗是否合适，能否避免遮挡正文、模态阻断和抢焦点？草稿切换/关闭语义是否有更简单可靠的方案？
6. 多窗口、本机主题和远端共享会话的范围是否明确？尤其是修改共享会话 RGB 时，是否会违反“只在本机试色”的预期？
7. 推荐 B 的服务端工作量与已有服务复用是否合适？格式、版本条件写入、断网、历史恢复是否足够而不过度设计？
8. 能否维持 DevBox 版本隔离、小补丁集、现有字体/图片粘贴/SSH 行为？是否误引入了新账号体系、第二套主题库或危险远端控制能力？
9. 第一版范围和上述阶段是否需要调整？列出必须先拍板的分歧，区分阻断问题和可后续改进。

审核输出建议：先给“可实施 / 需修改后实施 / 关键前提未成立”的结论，再按实际问题给证据、影响、建议修改和需要用户决定的事项。仅审核，不修改业务代码、不部署、不自动合并或发布。
